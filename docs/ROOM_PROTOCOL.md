# Phase 9 room architecture and protocol

## Authority and identity

The public Worker validates routes, origins, JSON sizes, scene IDs, and creation
inputs. It generates a random six-digit code and asks `ROOMS.getByName(code)` to
reserve it. The SQLite-backed `GameRoom` Durable Object serializes operations
through `blockConcurrencyWhile`; a live reservation returns 409 and allocation
tries another code (maximum 12 attempts). No eventually-consistent index or extra
directory service is required. All six-digit strings, including leading zeroes,
are valid codes.

Each new room has a separate random UUID. An expired code can be reused, but the
new room UUID and new credentials prevent old clients from resuming into it.
Room broadcasts contain only the shared `Room` shape. Private token hashes never
enter that shape. A player receives a UUID and 64-character opaque token in their
create/join response. Room creation credentials are server-generated. Join
credentials are generated by the browser and sent with a unique request UUID so a
lost successful response can be retried safely. The Durable Object stores only
SHA-256 token hashes. Treat the token as an anonymous bearer credential.

The frontend keeps credentials in tab-scoped sessionStorage, with an in-memory
fallback and visible warning if browser storage is unavailable. Refresh restores
the player in that tab. Closing the tab can lose the credential; joining from a
new tab asks for a nickname. Copying an invite shares only `/room/:code`.

The WebSocket authenticates in its first JSON message; credentials never appear
in URLs. The server sends no room state to unauthenticated sockets. A replacement
connection invalidates the earlier socket for that player, and its delayed close
event cannot mark the replacement offline. The old client stops retrying.

## HTTP routes

All paths are relative to the Worker origin. The frontend uses same-origin `/api`
through Vite's local proxy unless `VITE_API_BASE_URL` is configured.

| Method | Route                                         | Input                                            | Success                                                           |
| ------ | --------------------------------------------- | ------------------------------------------------ | ----------------------------------------------------------------- |
| GET    | `/api/health`                                 | —                                                | `{ ok: true }`                                                    |
| POST   | `/api/rooms`                                  | `{ sceneId, nickname }`                          | 201 `RoomSession`                                                 |
| GET    | `/api/rooms/:code`                            | —                                                | Public summary: id, code, sceneId, status, expiresAt, playerCount |
| POST   | `/api/rooms/:code/join`                       | `{ nickname, requestId, requestToken }`          | 201 `RoomSession`                                                 |
| GET    | `/api/rooms/:code/socket`                     | WebSocket upgrade + allowed Origin               | 101 upgrade                                                       |
| POST   | `/api/rooms/:code/recordings/:lineId`         | Raw allowed audio + authorization headers        | 201/200 stored recording metadata                                 |
| GET    | `/api/rooms/:code/render-inputs/:recordingId` | Bearer session + room/player/manifest headers    | Exact frozen private recording bytes                              |
| POST   | `/api/rooms/:code/results/:resultId`          | Raw MP4 + bearer/session/result/manifest headers | Committed authoritative result metadata                           |
| GET    | `/api/rooms/:code/results/:resultId`          | Bearer session + room/player headers             | Exact committed private MP4                                       |

`RoomSession` is `{ code, roomId, playerId, token }`. A join retry with the same
request UUID, nickname and secret returns the original session without reserving a
second player or nickname. Reusing the UUID with changed credentials is rejected.
Room creation is not automatically retried: if its successful response is lost,
an unused room may remain until expiry.

Recording uploads carry the anonymous token in `Authorization: Bearer`, plus room,
player, recording UUID and measured-duration headers. Credentials never enter the
URL. The Worker bounds the raw body to 5 MiB before forwarding it to the room DO.
The DO revalidates the token hash, room UUID, started state, canonical line and
server assignment. It accepts only the four MIME values produced by Phase 5.

Renderer reads carry the same anonymous bearer/session headers plus
`X-Manifest-Id`. The Durable Object requires the exact room UUID, a still-present
participant, `processing` state and a schema-valid matching frozen manifest. It
then maps the requested recording UUID to that manifest's server-held MediaStore asset.
The public route never accepts an asset ID, DO ID or storage prefix, never lists objects and returns
the exact object as `private, no-store`. An unlisted UUID, wrong manifest, missing
object or byte-size mismatch fails without mutating the room or manifest.

Prepared background reads use `/api/rooms/:code/render-background` with the same
session and exact `X-Manifest-Id` authority. The room verifies that its frozen manifest
contains that exact room route and that its own immutable background asset exists; the
browser cannot provide an asset ID or substitute a scene/current-Studio asset. A room
created with background A keeps its private A copy after Studio replacement with B or
scene deletion. Missing or unauthorized background fails the render and never permits a
fallback to source movie audio.

Final-result uploads carry a browser-generated result UUID and the exact frozen
manifest UUID in headers. The Worker bounds the body to 64 MiB. The room validates
the participant session, room UUID, `processing` state, manifest identity,
`video/mp4` content type, non-empty body and MP4 `ftyp` signature. MediaStore asset IDs,
DO IDs and scopes are never accepted as client fetch authority.

The UI gives the current host the predictable primary renderer role; other clients
show a truthful waiting state. The server nevertheless accepts a valid upload from
any current participant. The Durable Object serializes attempts: the first stored
and durably committed result wins, an exact result/manifest retry returns that same
metadata, and every different later result receives `RESULT_ALREADY_COMMITTED`.

Errors use `{ code, message }`. Codes are defined in
`shared/schemas/protocol.ts`. Typical statuses: 400 invalid input, 401 invalid
session, 403 denied origin, 404 missing/expired room, 409 duplicate nickname or
full/unavailable room, 413 oversized JSON, 429 rate limit, and 500 internal error.
Non-upgrade responses are non-cacheable. Logs do not deliberately include tokens
or raw request bodies.

## WebSocket discriminated unions

The canonical runtime validators and TypeScript unions are in
`shared/schemas/protocol.ts`.

Client → server:

```json
{ "type": "AUTH", "session": { "code": "012345", "roomId": "<uuid>", "playerId": "<uuid>", "token": "<64 hex characters>" } }
{ "type": "PLAYER_READY", "ready": true }
{ "type": "START_GAME" }
{ "type": "FINALIZE_RECORDINGS" }
{ "type": "LEAVE_ROOM" }
{ "type": "PING" }
```

Server → client:

```json
{ "type": "ROOM_STATE", "payload": "<validated Room object>" }
{ "type": "ERROR", "payload": { "code": "UNAUTHORIZED", "message": "Your room session is no longer valid. Join again." } }
{ "type": "LEFT_ROOM" }
{ "type": "PONG" }
```

The placeholders above describe structure, not literal valid credentials/state.
`PLAYER_READY`, `START_GAME`, `FINALIZE_RECORDINGS` and `LEAVE_ROOM` act on the authenticated socket
identity. Extra fields such as `playerId`, `hostId`, `status`, character IDs or
assignments are rejected. `START_GAME` carries no client-selected state. The
server resolves the room's selected scene and assigns its canonical characters.

The public `Room` state contains `startedAt`, which is `null` in `lobby` and an
integer timestamp after a successful start. The transition sets status to
`playing`; assigned character IDs remain on each player. The normal `ROOM_STATE`
broadcast is the only start/update representation clients need.

After a successful upload, `Room.recordings` exposes one validated metadata entry
per line: recording/player/line identifiers, private object key, MIME type, byte
size, client-measured duration and server upload timestamp. It never contains raw
audio, base64, Blob URLs, bearer credentials or R2 credentials. These entries let
clients derive authoritative recording progress. `Room.recordingProgress` is the
server-derived room/player view of required, uploaded and remaining counts. It is
computed from canonical lines, persisted assignments and matching authoritative
recordings; connection presence and client completion claims do not affect it.

Only the current host can send `FINALIZE_RECORDINGS`, and only while `playing` with
all required recordings present. Success atomically changes the room to `processing`
and persists `Room.recordingManifest`. Normal missing-recording, non-host and duplicate
requests return typed errors without disconnecting valid clients.

A successful final-result transaction streams the MP4 into the room's SQLite MediaStore
scope first, then persists the exact result metadata and `status: "finished"` together.
If the media write fails, no room metadata changes. If the durable metadata write fails, the new asset is deleted
best-effort and the frozen manifest/recordings remain in `processing` for retry.
Only after the durable write succeeds is the new room state broadcast.

Authorized participants retrieve only the exact committed result UUID while the
room is `finished`. The Durable Object maps it to the private object reference and
returns `private, no-store`; arbitrary keys, other result UUIDs, cross-room sessions
and prefix browsing are rejected. Reconnect and hibernation restore `finished`, the
manifest and result metadata without rerendering.

`revision` increases on persisted changes; clients ignore older state snapshots.
Ready controls display server-confirmed values. A transport heartbeat runs every
15 seconds; after 45 seconds without responses the active client reconnects.
Initial authentication/connection times out after 12 seconds. If the first socket
handshake fails, the client reads the public summary to distinguish a missing,
expired or code-reused room from a network interruption. Connection failures retry
up to six times with exponential delay and jitter, followed by manual retry.
Terminal authentication, expiry, and replacement errors stop automatic retries.

## Presence, hosting, and expiry

- Joining reserves a nickname and slot; a player is connected only after socket
  authentication. Maximum 12 players, including disconnected reservations.
- Only the connected current host can start, and only while the room is in
  `lobby`. At least one player must be connected and every connected player must
  be ready. Disconnected reserved players do not block the start and receive no
  new assignment.
- Character assignment is deterministic round-robin: canonical scene character
  order is distributed over connected player join order. Every character is
  assigned exactly once. Earlier players receive the extra characters when counts
  do not divide evenly; players beyond the character count receive none.
- Start succeeds once. Duplicate or invalid-state starts are rejected. Temporary
  disconnect, reconnect, host transfer, hibernation and runtime restoration never
  recalculate assignments or `startedAt`.
- Nicknames are trimmed and validated at 2–20 characters. Conflicts compare NFKC
  normalized lowercase values, including disconnected players.
- A disconnected player remains in the room for reconnection and becomes not
  ready. If the host disconnects, the first connected player in join order becomes
  host. The old host does not automatically reclaim hosting on return.
- If nobody is connected, retain the current host reference. A returning player
  takes hosting when the previous host is still offline. A host who explicitly
  leaves is replaced by a connected player, otherwise a remaining member.
- Explicit leave deletes the player and token hash, releases the nickname, sends
  `LEFT_ROOM`, and broadcasts remaining state. The last leave deletes room data.
- Joining, authenticating, readiness changes, game start, and leaving extend `expiresAt` by
  `ROOM_TTL_MS` (three hours by default). Reads, disconnects, and automatic PINGs
  do not extend it. An idle connected lobby therefore also expires.
- One Durable Object alarm handles expiry and unauthenticated socket deadlines.
  Expiry closes sockets, deletes persisted room data and removes all objects under
  the room's scoped MediaStore object. No paid scheduler is required. Failed best-effort media
  cleanup is logged; a future production bucket lifecycle remains defense in depth.
- Hibernation preserves authenticated socket attachments. A full runtime restart
  reconciles persisted presence against surviving sockets before serving state.

## Limits and development scope

HTTP JSON and WebSocket messages are limited to 4096 bytes. Recording bodies have
a separate 5 MiB limit. HTTP bodies are read
incrementally rather than trusting Content-Length. Binary commands are rejected.
Rooms accept at most 24 simultaneous sockets; unauthenticated sockets have 10
seconds to authenticate. Socket command traffic is limited to 30 messages per
10-second window; counters live in serialized attachments across hibernation.
Automatic PING/PONG uses Cloudflare's hibernation-compatible auto-response API.

Worker HTTP limits are best-effort, per-isolate counters: 180 requests/minute and
10 room creations/minute per Cloudflare-provided client IP. They are not a global
distributed quota and are insufficient for a large public launch. Origin checks
restrict browser use, but do not authenticate non-browser callers. Knowing a room
code permits joining by design. No public room-directory endpoint exists.

Phase 4 adds no playback commands to the room protocol. `status: "playing"`,
`startedAt`, presence and character assignments remain server-authoritative and
arrive through ordinary `ROOM_STATE` messages. Each browser loads the selected
scene's authorized static media and derives completed/current/upcoming dialogue
from the native video clock plus the canonical millisecond script. Play, pause and
seek are local controls: there is no shared playhead or claim of tight multi-device
synchronization. Refresh/reconnect restores the persisted playing state and roles,
but local playback restarts at zero. Placeholder media is never requested.

Recording bytes live in the room's SQLite MediaStore scope as ordered 1 MiB chunks. The
same recording UUID is idempotent. A replacement writes a server-generated asset and
durably commits its product metadata/private mapping before deleting the previous asset,
so a failed replacement preserves the last valid recording. Scope expiry covers any
orphan. There is no public storage URL or arbitrary read/write route; authenticated reads
are limited to an exact frozen manifest identity.

Phase 7 serializes final upload and finalization operations through the same Durable
Object. If the upload wins, finalization sees complete coverage; if finalization wins
while incomplete, it is rejected and the upload may finish normally. A frozen v1
manifest contains room/scene/source-media identity and exactly one canonical ordered
entry per required line with timing, authoritative player/character ownership and
the validated logical recording reference. It contains no raw media or secrets. Once the
room is `processing`, all upload/replacement requests are rejected and duplicate
finalization cannot create a competing manifest. Reconnect and hibernation restore
the persisted manifest unchanged.

Phase 8 composition still happens in the host browser. Phase 9 automatically uploads
the resulting Blob while retaining its local object URL; a failed upload can retry
with the same result UUID without rerendering. A successful commit broadcasts
`finished`, after which all clients prefer the authenticated shared MP4 experience.
Room-prefix expiry removes both recordings and result objects. Public deployment,
permanent hosting and AI/user-clip preparation remain later work.
Local integration tests use actual workerd/SQLite Durable Objects via Miniflare;
browser tests connect the production frontend to local Wrangler. No Cloudflare
account, remote resources, deployment, or paid infrastructure is required for
these checks.
